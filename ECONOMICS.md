## 6. Why Not Just RAG and Vector Stores?

RAG (Retrieval Augmented Generation) and Vector Stores have their place. They're excellent for search and Q&A over large document sets.

But they solve a different problem.

| RAG / Vector Stores | Spatial Context |
| :--- | :--- |
| Retrieves what *might* be relevant | Human selects what *is* relevant |
| Probabilistic (embedding similarity) | Deterministic (explicit pointers) |
| Searches through noise to find signal | Starts with signal only |
| Chunks lose structural context | Views preserve relationships |
| No architectural awareness | Structure is the interface |
| Optimised for search | Optimised for building |

**The fundamental difference:**

RAG asks: "What documents might be relevant to this query?"

Views ask: "What is the exact scope of this task?"

RAG is retrieval. Views are intent.

**The chunking problem:**

Vector stores work by splitting content into chunks and embedding them. This works for text search. But code isn't text - it's structure. When you chunk a codebase, you lose the relationships between components. The AI retrieves fragments without understanding how they connect.

Views preserve structure. The AI sees modules, dependencies, and boundaries - not isolated chunks.

**The noise problem:**

RAG retrieves the "top k" most similar results. But similar isn't the same as relevant. You get noise - tangentially related files, old versions, deprecated code - all consuming tokens and confusing the model.

Views are precise. You Lasso exactly what matters. Nothing more.

**The right combination:**

For AI-assisted development at scale, you may need both - but the View comes first. You define the boundary with spatial selection, then RAG can operate within that bounded context if needed.

The scalpel before the search.
